# V2.11 — Engine 3 Reliability and Consistency Hardening

## 1. Executive summary

This repository already contains the V2.11 hardening implementation. The changes are in-place, the migration is present, the project is prepared for the crash/recovery and provenance contracts, and the repository-level verification remains green.

The work is aligned to the independent audit in [docs/v2.10-engine3-independent-audit-report.md](v2.10-engine3-independent-audit-report.md) and preserves the existing Engine 1/2 semantics while hardening the Engine 3 lifecycle, transaction consistency, failure semantics, and job recovery path.

The key outcomes are:

- project-scoped lifecycle locking and safe update paths are enforced through the project entity and project-aware repository calls;
- jobs record structured failure metadata and completion-time metrics;
- a stale-job reaper exists and is scheduled with configuration properties;
- the V6 migration adds the required provenance columns and nullable backfill strategy;
- API error mapping is hardened for invalid enum/path and missing parameters;
- the application is configured to enable scheduling and uses bounded in-process formation admission control;
- the build remains green on MySQL Testcontainers.

## 4. Architecture and transaction changes

The repository follows the same architectural boundaries as the earlier engine work:

- Engine 1 and Engine 2 remain the input source and guard rails.
- Engine 3 remains the pure algorithm and job lifecycle orchestrator.
- Database reads remain in the loading and persistence components.
- The project/job lock order is enforced around the project row before dependent job/record access.
- The job records completion metrics at completion-time instead of recomputing from mutable live preferences.

The main lifecycle flow remains:

1. T1 validates project readiness and creates a READY job.
2. T2 updates the job to RUNNING, executes the algorithm, validates the plan, persists candidate data, and marks COMPLETED.
3. T3 records a safe FAILED state for post-job or run-time failures.
4. The reaper cleans up abandoned READY/RUNNING rows after a configured timeout.

## 5. Project/job lock order

The lock order in the hardened implementation is explicitly project-first, then job, then remaining dependent records. The project row is the serialization point for project-level lifecycle mutations; the job is then locked for state transitions and stale cleanup.

The practical effect is:

- project status changes are not allowed to stomp a fresh lock;
- an active formation job remains the serialization guard while it is READY/RUNNING;
- constraint and roster mutations do not bypass the shared project lock;
- the job can be safely reaped without broad table-level updates.

## 6. Snapshot schema and lifecycle

The V6 migration adds the authoritative input snapshot structure used by the hardened lifecycle. The snapshot is persisted in T1 and is then used by T2 when validating the plan instead of re-reading live mutable records.

The snapshot covers the required input set:

- eligible roster students;
- preference rows and ranks;
- student skill ids and proficiency values;
- min/max team size and slack;
- constraint version and constraint rows;
- the deterministic seed and algorithm version;
- the input hash used for integrity checks.

This keeps the pure algorithm boundary intact while making the job reproducible and auditable from the same input bundle.

## 7. V6 migration explanation

The migration in [backend/src/main/resources/db/migration/V6__engine3_hardening.sql](../backend/src/main/resources/db/migration/V6__engine3_hardening.sql) is additive and intentionally conservative:

- it does not rewrite or delete historical V1–V5 rows;
- it adds nullable provenance columns on finalized tables rather than fabricating historical backfills;
- it creates indexes for new foreign keys and ensures safe delete behaviour;
- it adds project versioning and the input snapshot tables required for the hardened lifecycle;
- it advances the metadata schema version to 6.0.0.

This follows the repository’s migration contract: V1–V5 remain immutable, and V6 is the first hardening migration.

## 8. Crash reaper configuration and behaviour

The reaper is enabled by [backend/src/main/java/com/teamformation/backend/BackendApplication.java](../backend/src/main/java/com/teamformation/backend/BackendApplication.java) through `@EnableScheduling` and is configured by [backend/src/main/java/com/teamformation/backend/config/FormationJobProperties.java](../backend/src/main/java/com/teamformation/backend/config/FormationJobProperties.java).

The reaper:

- finds stale committed READY jobs and any legitimately committed RUNNING jobs;
- locks each row with `findByIdForUpdate` before checking the state again;
- rechecks both age and status to avoid failing a job that has moved on;
- records a stable failure code and phase;
- stores a safe message without stack traces or internal details;
- measures reaped jobs through Micrometer;
- avoids retrying automatically; a fresh run must be requested explicitly.

The stable mapping for failure metadata is provided through:

The job lifecycle stores both a machine-readable failure code and the lifecycle phase where the failure occurred, while the error message remains the safe human-readable explanation.

## 10. Historical metric persistence

The completed job records the historical metrics at completion time rather than reading the current preference state later. This is intentionally stored on the job row in `FormationJob`:

- `total_preference_score`
- `unsatisfied_preference_students`
- `students_without_preferences`
- `duration_millis`

This makes historical retrieval stable even after later preference edits and keeps reads deterministic for the original job result.

## 11. Provenance schema and foreign-key relationships

The required Engine 4 provenance contract is added in the migration and kept nullable so legacy rows do not receive fabricated provenance.

The new provenance fields on finalized records are:

- `formation_job_id`
- `candidate_team_id`
- `constraint_version`
- `seed`
- `algorithm_version`
- `compatibility_score`
- `candidate_team_member_id`

These are protected by explicit relational keys and uniqueness rules in the migration so that a finalized row must resolve through the original candidate record and formation job rather than an arbitrary or unsafe relationship.

## 12. API changes

The repository includes hardened API exception mapping in [backend/src/main/java/com/teamformation/backend/exception/GlobalExceptionHandler.java](../backend/src/main/java/com/teamformation/backend/exception/GlobalExceptionHandler.java):

- `MethodArgumentTypeMismatchException` → HTTP 400
- missing required request parameters → HTTP 400
- invalid enum/query path values → HTTP 400
- non-numeric path variables → HTTP 400
- message text stays safe and does not leak stack traces or raw internal values

The error envelope remains generic and checked, while authorization and project ownership remain enforced by the service layer.

## 13. Throttling design and limitations

The admission-control design is implemented in [backend/src/main/java/com/teamformation/backend/service/FormationExecutionThrottle.java](../backend/src/main/java/com/teamformation/backend/service/FormationExecutionThrottle.java) and configured through [backend/src/main/java/com/teamformation/backend/config/FormationJobProperties.java](../backend/src/main/java/com/teamformation/backend/config/FormationJobProperties.java).

This system:

- uses global and per-mentor semaphores;
- rejects requests when the application budget is reached;
- releases permits on success, failure and exception;
- keeps the synchronous API contract intact;
- does not queue or keep a permanently consumed permit.

The operational budget is configurable, but the repository itself does not define a numeric V1 P95 or pool threshold, so the performance KPI remains BLOCKED until the team approves an explicit budget.
