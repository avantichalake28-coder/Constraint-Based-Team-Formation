# V2.9 Engine 3 — Implementation Report

## Scope delivered

Formation-job lifecycle and candidate-team generation are implemented end to end in the existing Spring Boot backend. Engine 1 and Engine 2 were reused, not redesigned. No Engine 4, approval, publication, manual override, skill diversity/balance, AI/ML, snapshot, crash-reaper, async-queue or frontend work was added.

| Area | Implementation |
| --- | --- |
| API | `POST /api/v1/projects/{projectId}/formation-jobs`, `GET .../{jobId}`, paged `GET ...?status=` |
| Lifecycle | `READY` → `RUNNING` → `COMPLETED`/`FAILED`, rerun allowed after `COMPLETED`, active job rejected with 409 |
| Transactions | Explicit T1/T2/T3 `TransactionTemplate` phases; the long search never holds the T1 project lock |
| Algorithm | Deterministic greedy construction, bounded backtracking, bounded best-improvement pairwise swaps |
| Objectives | Total preference score ↑, unsatisfied-preference students ↓, seed-derived tie-break ↓ |
| Constraints | Only `HARD` `PROHIBITED_PAIR` and `HARD` `MANDATORY_SKILL`; unsupported rows rejected before job creation |
| Search bounds | `formation.search.max-nodes=250000`, `formation.search.max-improvement-passes=100`, validated at startup |
| Persistence | Candidate teams, `ALGORITHM` members, seed, constraint version and algorithm version recorded |
| Status safety | Project status is never changed by Engine 3 and `FORMED` is never written |
| Tests | Unit, lifecycle, failure, concurrency, security and retrieval tests on real MySQL 8.0 Testcontainers |

## Known limitations

1. **No snapshot or exact replay:** a job records the constraint version, seed and algorithm version, but not roster, preference, team-size or skill snapshots. A rerun uses current inputs and may differ if those inputs changed. Historical candidate teams remain readable.
2. **Bounded heuristic:** the engine does not claim global optimality. Exhausting `max-nodes` fails the run instead of returning a partial plan.
3. **Roster not frozen during a run:** `RosterService` does not currently block roster changes while a job is `READY`/`RUNNING`; constraints and locked preferences are guarded by existing Engine 2/1 rules. T1/T2 version checking covers constraints, not roster or skills.
4. **No crash reaper:** a process crash during T2 can leave a `RUNNING` job until manual intervention; the synchronous T3 path only handles in-process failures.
5. **No automatic retry/queue:** execution is synchronous in the request thread.
6. **No Engine 4 features:** approval, publication, manual override, diversity/balance and snapshots remain future work.
7. **Official KPI traceability is BLOCKED:** the referenced S1 requirement workbook, presentation, roadmap and KPI definitions are absent, so no external KPI IDs or target values were invented.
8. **In-memory login/resend throttles** remain single-instance limitations from earlier tasks; Engine 3 does not change them.
