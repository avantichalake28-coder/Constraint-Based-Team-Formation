# Decision Log

Status values:

* **DECIDED** — confirmed by the user or already fixed by project policy.
* **ASSUMPTION** — recorded because the task does not fully specify the choice; revisit when the referenced engine work starts.

| # | Status | Area | Decision / assumption | Reason |
| --- | --- | --- | --- | --- |
| 1 | DECIDED | Team size | Fixed team size (workbook FR-04) is replaced by mentor-set `min_team_size`, `max_team_size` and `team_size_slack` with defaults 2, 4 and 1. | User decision. Mentors need to set a range, including one optional extra student in a team of 5. |
| 2 | DECIDED | Team size | These fields may move into a versioned constraint configuration in the Engine 2 task. | User note; no team-size planner is implemented in Task 2.2b. |
| 3 | ASSUMPTION | SRN | The SRN is stored only on `student_profiles` (`srn NOT NULL UNIQUE`) and removed from `users`, because mentors and admins do not have an SRN. | Required and unique for students, but not required on every user. A profile is the student-only record. |

| 5 | DECIDED | SRN | Pattern `^[0-9]{2}FE[0-9]{2}[A-Z]{3}[0-9]{3}$`, enforced by a case-sensitive MySQL CHECK and the same Bean Validation pattern in Java. Java normalises to uppercase. | User requirement; prevents lowercase SRNs and malformed values. |
| 6 | DECIDED | Roster | `project_roster` remains the mentor-built eligibility list, with `UNIQUE(project_id, student_id)` and no course or enrollment table. | User requirement; eligibility lives on the roster. |

| 8 | DECIDED | Preferences | `is_mutual` is dropped. Mutuality is derived later and is not stored. | User requirement; derived data. |
| 9 | DECIDED | Preference lock | `projects.preferences_locked_at` is nullable and can be set by automatic deadline lock or by the mentor early. | User requirement; no locking behaviour is implemented in Task 2.2b. |

| 14 | ASSUMPTION | Skills | The existing `ConstraintRuleType.MANDATORY_VERIFIED_SKILL` enum constant is retained even though skill verification is gone. | It is a constraint-rule label, not the removed verification status; changing it would be unrelated schema/enum churn. | 25 | DECIDED | Tests | Constraint tests run on real MySQL 8.0 through Testcontainers. The image is pinned to `mysql:8.0`; H2 is never used and a missing Docker daemon fails the build. | Prevents dialect drift and silent skips. |
| 26 | ASSUMPTION | Schema naming | `changed_by` and `finalized_by` use the names given in the task rather than adding `_id` suffixes. | Follows the task wording; foreign keys still reference `users.id`. |
| 27 | ASSUMPTION | Data safety | All V2 tables were empty when V3 was written. The development database had only V1 applied, so the affected V2 tables did not exist and contained no rows. | No data was deleted or modified by the migration. |
| 28 | DECIDED | Repositories | All Spring Data JPA repositories live in `com.teamformation.backend.repository`. Derived query methods are preferred; JPQL is used only for `ProjectRepository.findByIdForUpdate`, where the pessimistic lock hint is clearer than a derived name. Repositories carry no `@Transactional` and no business logic. | One package convention, applied consistently beside the existing `AppMetadataRepository`, matching the base package and keeping the persistence layer easy to scan. |
| 29 | ASSUMPTION | Password policy | Registration and mentor creation require a password of at least 10 characters. No composition rule (upper/lower/digit/symbol) is imposed. | The task fixed the minimum length but not a complexity policy; 10 characters was chosen as a reasonable baseline and can be tightened when the product owner confirms a policy. |
| 30 | ASSUMPTION | Email verification | A verification token is valid for 24 hours from registration. Expired, used and unknown tokens all return the same generic 400 response. | The task required expiry and reuse rejection but not the duration or message wording; a single generic error avoids leaking token state. |
| 31 | ASSUMPTION | Registration conflicts | A duplicate email (case-insensitive) or duplicate SRN returns HTTP 409 with the neutral message "An account with the provided details already exists" rather than naming the conflicting field. | The task asked for neutral duplicate handling; the exact status/message were unspecified. Neutral wording avoids account enumeration through registration. |
| 32 | ASSUMPTION | Mentor accounts | Admin-created mentors are active immediately, have no SRN and no student profile, and receive no verification email. | Mentors cannot self-register and the task did not require email verification for them; the admin is the trusted creator. |
| 33 | ASSUMPTION | JWT lifetime | Access tokens last 60 minutes. There is no refresh token, revocation list or logout endpoint. | The task fixed HMAC-SHA256, a subject/role claim and per-request database validation, but not the lifetime or refresh design. Immediate database lookup covers deactivation and role changes. |
| 34 | ASSUMPTION | Login throttling | Five failed attempts for one email within fifteen minutes return HTTP 429. Counters are held in a `ConcurrentHashMap` inside one JVM and reset on restart or successful login. | The task required 5 failures per email per 15 minutes but did not specify shared storage. A multi-instance deployment must replace this with a shared store such as Redis; documented as a known limitation. |
| 35 | ASSUMPTION | Candidate-team foreign key | V4 replaces `fk_teams_formation_job` (`ON DELETE SET NULL`) with `ON DELETE CASCADE` when making `formation_job_id` NOT NULL. | MySQL rejects a NOT NULL column in a SET NULL foreign key. A candidate team cannot exist without its run, so cascading the delete is the only behaviour consistent with the new constraint. |
| 36 | ASSUMPTION | Test mail health | `management.health.mail.enabled` is false only in the test profile. | The integration tests replace `JavaMailSender` with a mock, which leaves Boot's mail health contributor without contributors and fails context startup (`'beans' must not be empty`). Production keeps the indicator enabled. |
| 37 | ASSUMPTION | Registration mail failure | The verification email is sent inside the registration transaction, so an SMTP failure rolls back the user, profile and token. | The task did not define retry or queued-mail behaviour. Atomic failure avoids accounts that can never receive a verification link; a future outbox pattern can replace it. |
| 38 | ASSUMPTION | JSON strictness | Unknown request properties are rejected with HTTP 400 for every endpoint, not only registration. | The task explicitly named `phone`/`role` on registration; applying the same Boot/Jackson setting globally is simpler, safer and tested through the admin endpoint too. |
