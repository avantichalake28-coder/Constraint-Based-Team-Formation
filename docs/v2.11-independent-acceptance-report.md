# V2.11 Independent Acceptance Report

## Executive summary

This audit is based on the repository as it exists in the working tree, not on the implementation narrative alone. The codebase contains substantial V2.11 hardening work and the project-level architecture is consistent with the intended Engine 3 reliability model. However, the implementation is not yet ready for formal acceptance because the repository does not yet provide direct, end-to-end evidence for several mandatory V2.11 recovery and concurrency claims that the acceptance gate requires.

### Decision

Status: DEFERRED — not ready for formal acceptance.

### Why the implementation is strong

The repository contains the major V2.11 constructs expected by the independent audit:

- project-scoped serialization via pessimistic write locking in [backend/src/main/java/com/teamformation/backend/repository/ProjectRepository.java](../backend/src/main/java/com/teamformation/backend/repository/ProjectRepository.java), [backend/src/main/java/com/teamformation/backend/service/ProjectService.java](../backend/src/main/java/com/teamformation/backend/service/ProjectService.java), [backend/src/main/java/com/teamformation/backend/service/RosterService.java](../backend/src/main/java/com/teamformation/backend/service/RosterService.java), and [backend/src/main/java/com/teamformation/backend/service/PreferenceService.java](../backend/src/main/java/com/teamformation/backend/service/PreferenceService.java);
- T1/T2/T3 lifecycle orchestration in [backend/src/main/java/com/teamformation/backend/service/FormationService.java](../backend/src/main/java/com/teamformation/backend/service/FormationService.java);
- immutable formation-input snapshot persistence and verification in [backend/src/main/java/com/teamformation/backend/engine/formation/persistence/FormationInputSnapshotStore.java](../backend/src/main/java/com/teamformation/backend/engine/formation/persistence/FormationInputSnapshotStore.java);
- stale job recovery logic in [backend/src/main/java/com/teamformation/backend/service/FormationJobReaper.java](../backend/src/main/java/com/teamformation/backend/service/FormationJobReaper.java) and configuration in [backend/src/main/java/com/teamformation/backend/config/FormationJobProperties.java](../backend/src/main/java/com/teamformation/backend/config/FormationJobProperties.java);
- structured failure metadata in [backend/src/main/java/com/teamformation/backend/entity/FormationJob.java](../backend/src/main/java/com/teamformation/backend/entity/FormationJob.java);
- V6 migration for snapshots and provenance in [backend/src/main/resources/db/migration/V6__engine3_hardening.sql](../backend/src/main/resources/db/migration/V6__engine3_hardening.sql);
- provenance fields in [backend/src/main/java/com/teamformation/backend/entity/FinalizedTeam.java](../backend/src/main/java/com/teamformation/backend/entity/FinalizedTeam.java) and [backend/src/main/java/com/teamformation/backend/entity/FinalizedTeamMembership.java](../backend/src/main/java/com/teamformation/backend/entity/FinalizedTeamMembership.java);
- safer API mapping in [backend/src/main/java/com/teamformation/backend/exception/GlobalExceptionHandler.java](../backend/src/main/java/com/teamformation/backend/exception/GlobalExceptionHandler.java).

### Why the implementation is not yet acceptance-ready

The repo contains strong code and a green test suite, but the V2.11 acceptance bar is stricter than a plain build pass. The key issue is proof: the repository does not yet exercise several of the mandatory V2.11 acceptance scenarios in a direct, explicit, real-DB test set.

The clearest gap is crash recovery. The stale job reaper exists, but the repo does not contain a direct real-DB test that creates an abandoned READY job, invokes the reaper, and proves it is converted to FAILED and re-usable. This is especially visible in the test configuration comments in [backend/src/test/resources/application-test.yaml](../backend/src/test/resources/application-test.yaml), which explicitly say that “Reaper tests call reapStaleJobs(Instant) directly,” yet no corresponding reaper test class or invocation is present in the repository under [backend/src/test/java/com/teamformation/backend](../backend/src/test/java/com/teamformation/backend).

The repository also does not provide formal acceptance evidence for the full V2.11 test matrix described by the independent audit. It has one concurrency test for the active-job race in [backend/src/test/java/com/teamformation/backend/Engine3FormationConcurrencyIntegrationTest.java](../backend/src/test/java/com/teamformation/backend/Engine3FormationConcurrencyIntegrationTest.java), but not the full set of real-DB concurrency, snapshot, stale-job, historical metric, and provenance checks required by the V2.11 acceptance criteria.

Finally, the operational performance KPI remains unresolved: the configuration supports a bounded execution budget in [backend/src/main/java/com/teamformation/backend/config/FormationJobProperties.java](../backend/src/main/java/com/teamformation/backend/config/FormationJobProperties.java), but there is no numerical V1 latency or pool budget in the repository that can be audited for a formal performance acceptance claim.

## Critical evidence from the repository

### 1. The actual V2.11 hardening patterns are present

The key engineering paths are implemented in the service and persistence layers:

- T1 persists a READY job and immutable input snapshot in [FormationService.java](../backend/src/main/java/com/teamformation/backend/service/FormationService.java);
- T2 reconstructs from the snapshot and validates before completion in [FormationService.java](../backend/src/main/java/com/teamformation/backend/service/FormationService.java);
- T3 marks FAILED with structured failure metadata in the same service;
- stale jobs are discovered and failed by [FormationJobReaper.java](../backend/src/main/java/com/teamformation/backend/service/FormationJobReaper.java);
- V6 adds the schema contract in [V6__engine3_hardening.sql](../backend/src/main/resources/db/migration/V6__engine3_hardening.sql).

This is materially consistent with the V2.11 objective.

### 2. The repository does not yet prove the recovery requirement end-to-end

The test profile states:

> “Keep the scheduled stale-job sweep out of the test path. Reaper tests call reapStaleJobs(Instant) directly and therefore do not depend on wall time.”

See [backend/src/test/resources/application-test.yaml](../backend/src/test/resources/application-test.yaml).

The omission is important: the repository does not contain a matching reaper test class or any invocation of `reapStaleJobs(Instant)` under [backend/src/test/java/com/teamformation/backend](../backend/src/test/java/com/teamformation/backend). A spec-level mechanism exists, but the proof path is not in the repo. A formal acceptance document cannot treat a code path as proven if the repository has no direct evidence that it has been executed against the real database.

### 3. The concurrency coverage is narrow

The repo contains one active-job concurrency test in [Engine3FormationConcurrencyIntegrationTest.java](../backend/src/test/java/com/teamformation/backend/Engine3FormationConcurrencyIntegrationTest.java), and it does exercise a real, MySQL-backed race. That is valuable. It is not, however, the complete V2.11 concurrency matrix described in the audit and acceptance criteria. The repository does not contain direct tests for:

- simultaneous T1 requests with barrier-based serialization;
- roster mutation during T2;
- preference replacement during T2;
- skill change between T1 and T2;
- constraint save during a paused T2;
- historical metric stability after later preference edits.

This gap matters because the real audit goal is not just “the code looks right,” but “the required failure modes are proven under real database timing.”

### 4. The performance KPI is still a project decision, not a code result

The code supports execution throttling in [FormationExecutionThrottle.java](../backend/src/main/java/com/teamformation/backend/service/FormationExecutionThrottle.java) and configuration in [FormationJobProperties.java](../backend/src/main/java/com/teamformation/backend/config/FormationJobProperties.java), but no repository-managed budget or measured V1 threshold is attached to the acceptance requirement. That means the V2.11 performance KPI is still blocked until the team defines and verifies the agreed budget.

## Acceptance verdict

### Final recommendation

Do not sign off V2.11 for formal acceptance yet.

### Acceptable path to sign-off

The following are required before acceptance is defensible:

1. Add and run a real DB reaper test that creates an abandoned READY job, calls the reaper, and proves the row becomes FAILED and is reusable.
2. Add and run the remaining V2.11 race tests called out in the acceptance criteria, using Testcontainers and real DB timing.
3. Capture a single final `clean verify` run showing the project passes at the end of the acceptance cycle.
4. Declare and measure the V1 execution budget and P95 threshold, or explicitly mark the performance KPI as blocked for a later milestone.

Only after those steps are complete can V2.11 be treated as an auditable, crash-recoverable, concurrency-safe Engine 3 foundation rather than a strong but still incomplete hardening pass.

---

## Conclusion

The repository contains a credible V2.11 implementation and the major design elements are in place. That is enough to justify continued engineering work and a likely future sign-off, but it is not enough for a formal acceptance stamp today. The missing proof is concentrated in the crash-recovery and concurrency acceptance scenarios, and the performance KPI remains unresolved. The repo is therefore better described as “substantially implemented and green in broad coverage” than “fully accepted for formal V2.11 sign-off.”
