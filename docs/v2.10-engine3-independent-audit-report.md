## A. Executive Summary

### A.1 Overall assessment

Engine 3 is functionally complete, internally coherent, and unusually well tested for a student project. It reuses Engine 1 and Engine 2 correctly, keeps the algorithm pure and bounded, persists a validated plan atomically, records the seed/algorithm/constraint provenance that exists today, and has solid role/ownership authorization. The independent build is green: **310 tests, 0 failures, 0 errors, 0 skipped**.

The implementation is **not yet safe to treat as a fully concurrent, crash-tolerant production engine**, and it is **not yet a complete provenance foundation for Engine 4**. The audit found:

- **0 CRITICAL** findings: no unconditional data corruption, no authorization bypass, no wrong-result defect in the normal sequential path, and no hard-constraint violation in a single-actor run.
- **4 HIGH** findings: three concurrent-mutation races around the preferences-lock/team-size/skill inputs, plus a constraint-freeze race that can commit a plan under an outdated constraint version.
- **10 MEDIUM** findings: crash recovery, post-completion constraint mutability, historical metric drift, input snapshot/replay, structured failure reporting, Engine 4 provenance, candidate lifecycle, error mapping, throttling, and test gaps.
- **6 LOW** findings: idempotency, data minimization, DB-vs-service guarantees, isolation documentation, V2.9 documentation drift, and local-search time bounding.

### A.2 Why the decision is CONDITIONALLY ACCEPTED

The engine is acceptable for the intended **synchronous, single-actor V1 demonstration/use** where one mentor triggers a run and no other actor mutates the same project at the same time. In that mode the normal path is correct, the plan is validated, persistence is atomic, and the API is authorized.

It is **not accepted unconditionally** because:

1. A student can change skills during a run, and a student whose skills were used for mandatory-skill coverage can remove that coverage before commit (F-01).
2. Roster, preference and team-size mutations can slip past the preferences lock because those services do not take the project row lock (F-02), and `updateProject`/`publishProject` can overwrite a freshly set lock with a stale full-entity write (F-03).
3. A constraint version can be committed while T2 is running because the active-job check uses a consistent-read snapshot taken before the project lock, and T2 does not hold the project lock (F-04). This is derived from MySQL `REPEATABLE READ` semantics and is the one HIGH finding that was **not** reproduced experimentally (no targeted test exists).
4. A process crash after T1, or during T2, leaves a committed `READY` job with no reaper, permanently blocking future runs and constraint changes for that project (F-05).

The mandatory remedy is **V2.11 — Engine 3 Reliability and Consistency Hardening**, described in Section N. Engine 4 must not begin finalization work until V2.11 closes F-01 through F-05 and provides the provenance contract described in Section M.

| --- | --- | --- | --- | --- | --- |

### D.3 Key integration observations

1. **T1 and T2 load independently.** `createReadyJob` calls `formationInputLoader.load(...)` at `FormationService.java:189–190`; `executeJob` calls it again at `:268–269`. There is no input snapshot table and no input hash. This is deliberate under decision 73, but it means “same run” is only guaranteed while every input is unchanged.
2. **Feasibility is checked in T1 only.** `requireFeasible` (`:212–241`) runs the Engine 2 planner/checker before the job is created. T2 does not re-run the same feasibility report; it relies on the engine’s own no-valid-plan path. If inputs change between T1 and T2, T2 may fail with a different reason than T1 predicted.
3. **The constraint version is recorded but not the constraint rows.** `FormationJob` stores `constraintVersion`; `FormationInput` carries the version and the loaded rules. There is no persisted copy of the rule rows used by a completed job.
4. **The pure engine is correctly isolated.** `FormationEngine` receives immutable `FormationInput` and never touches a repository; `FormationInputLoader` and `FormationPlanPersister` own I/O. This is a good architectural boundary and should be preserved.
5. **Project status is never advanced by Engine 3.** A successful run leaves the project at `PREFERENCES_LOCKED`; `FORMED` is never written. Engine 4 will need an explicit transition and finalization workflow.

## E. Transaction Phases, Job Lifecycle, and Failure Handling

### E.1 T1 — create the READY job

`FormationService.startFormation` (`:151–168`) is deliberately not transactional. It obtains the mentor, generates a non-negative seed, and executes T1 via `TransactionTemplate` (`:156–157`).

`createReadyJob` (`:174–197`) does, in order:

1. `projectRepository.findByIdForUpdate(projectId)` — pessimistic write lock (`:175`).
2. Compare `project.mentor.id` with the authenticated mentor; mismatch is reported as 404 (`:177–179`).
3. `requireFormationReady(project)` (`:199–210`): status must be `PUBLISHED` or `PREFERENCES_LOCKED`, and `projectService.arePreferencesLocked(project)` must be true.
4. `formationJobRepository.existsByProjectIdAndJobStatusIn(projectId, [READY, RUNNING])` — reject a second active job (`:182–185`).
5. `constraintConfigurationService.loadCurrentConfiguration(projectId)` (`:187–188`).
6. `formationInputLoader.load(...)` (`:189–190`).
7. `requireFeasible(input)` (`:191`, `:212–241`).
8. Create and `saveAndFlush` the `FormationJob` with status `READY`, seed, algorithm version and constraint version (`:193–196`).

T1 commits the `READY` row. Pre-job failures roll back T1 and create no job, which is correct and explicitly tested.

### E.2 T2 — run and persist

`startFormation` calls `transactionTemplate.executeWithoutResult(status -> executeJob(jobId))` (`:161`). `executeJob` (`:247–284`) does:

1. `formationJobRepository.findByIdForUpdate(jobId)` — pessimistic write lock on the job row (`:248`).
2. `job.canStart()` requires `READY` (`:251–254`).
3. `job.markRunning(Instant.now())` and `saveAndFlush` (`:256–257`). **This RUNNING state is uncommitted until T2 commits.**
4. `constraintConfigurationService.loadCurrentConfiguration(project.getId())` (`:260–261`).
5. Compare `configuration.version()` with `job.getConstraintVersion()`; mismatch is a 409 conflict (`:262–266`).
6. `formationInputLoader.load(...)` (`:268–269`).
7. `formationEngine.form(input, searchLimits)` (`:270`).
8. `formationPlanValidator.validate(input, plan)` (`:271`).
9. `formationPlanPersister.persist(project, job, plan)` (`:272`).
10. Count persisted teams and members and compare with the validated plan (`:274–280`); mismatch throws `IllegalStateException`.
11. `job.markCompleted(Instant.now())` and `saveAndFlush` (`:282–283`).

Because steps 3–11 are one transaction, a reader never sees a committed `RUNNING` job for this synchronous implementation. It sees either the committed `READY` row (before T2 commits) or the committed `COMPLETED` row (after T2 commits). A crash rolls the whole transaction back to `READY`.

### E.3 T3 — record a failure

`startFormation` catches any `RuntimeException` from T2 (`:162–165`), calls `markFailed(jobId, failure)`, then rethrows a mapped API failure. `markFailed` (`:290–308`) opens a **new** transaction, locks the job row, returns if the job is missing or no longer READY/RUNNING, otherwise calls `job.markFailed(safeReason(failure), now)` and flushes. If T3 itself throws, it logs and swallows (`:305–307`), leaving the original API failure to propagate.

`safeReason` (`:310–327`) maps only the known formation exceptions to their messages; unknown exceptions become `"Team formation failed with an internal error"`. The reason is truncated to 2,000 characters, and `FormationJob.markFailed` truncates again. `Engine3FormationFailureIntegrationTest` proves that a simulated persistence failure leaves one `FAILED` job, zero candidate rows, and a reason that does not contain the injected exception text.

### E.4 Lifecycle state machine

| From | To | Trigger | Committed visibility |
| --- | --- | --- | --- |
| — | `READY` | T1 commit | Visible |
| `READY` | `RUNNING` | T2 `markRunning` | **Not visible** until T2 commits |
| `RUNNING` | `COMPLETED` | T2 `markCompleted` + commit | Visible |
| `READY` / `RUNNING` | `FAILED` | T3 after T2 rollback | Visible after T3 commit |
| `COMPLETED` | — | Terminal | Rerun creates a new job |
| `FAILED` | — | Terminal | Rerun creates a new job |

There is no retry, resume, cancel or heartbeat transition.

### F.1 Scenario A — roster student removed before T2

**Question:** Can a rostered student be removed after T1 loads the input and before T2 uses it, and what is the effect?

**Possible?** Sequentially, no: `RosterService.removeFromRoster` (`RosterService.java:170–192`) loads the project and rejects the removal with 409 when `projectService.arePreferencesLocked(project)` is true (`:173–177`). Formation requires preferences to be locked in T1, so by the time a job exists, a normal removal is blocked. The removal also refuses if the student has preferences, candidate memberships or finalized memberships (`:183–189`).

**However**, the guard is a check-then-act on a **non-locking** project read. `RosterService.removeFromRoster` uses `requireOwnedProject` → `projectRepository.findByIdAndMentorId` (`:194–197`), not `findByIdForUpdate`. `ProjectService.lockPreferences` uses `findByIdForUpdate` (`ProjectService.java:180`). Under MySQL `REPEATABLE READ`, the roster transaction can establish its read view before the lock commits and therefore see “unlocked” after the lock has committed. The removal can then write. This is F-02.

**Blocked?** Yes in the ordinary sequential case; **not reliably blocked** in the concurrent lock-transition case.

**Inconsistent output?** If the removal commits before T2 loads the roster, T2 simply plans with fewer students; the planner is recomputed and capacity matches, so the plan is internally consistent but differs from T1’s feasibility view. If the removal commits after T2’s roster query but before T2 commit, T2 can persist a candidate membership for a student who is no longer on the roster. `candidate_team_members.student_id` has a foreign key to `users`, not to `project_roster`, so the database does not reject this. The result is a valid-looking plan containing a non-rostered student.

**Hard-constraint violation?** Not in the constraint sense: prohibited pairs and mandatory skills are re-evaluated from the T2 input. A prohibited pair that references the removed student becomes inert because the student is not assigned. The semantic violation is the roster invariant, not a hard constraint.

**DB integrity intact?** Foreign-key and uniqueness integrity remain intact. Semantic integrity relative to the roster is broken in the race case.

**Smallest safe solution:** Make roster mutation acquire the same project row lock as `lockPreferences` and T1 (`findByIdForUpdate`) before checking the lock, and add a roster/input version or hash to the job so T2 can reject a changed roster. Failing that, snapshot the roster in T1 and load it in T2. The lock alone closes the ordinary race; the snapshot also gives Engine 4 replay.

### F.2 Scenario B — preference change after input load

**Question:** Can a student change preferences after T1 loads them and before T2 commits?

**Possible?** Sequentially, no. `PreferenceService.replaceMyPreferences` (`PreferenceService.java:68–119`) rejects when preferences are locked (`:75–78`) and also requires project status `PUBLISHED` (`:79–81`). Once `lockPreferences` commits, the status becomes `PREFERENCES_LOCKED`, so both guards fail. Again, the read is non-locking (`findById` at `:72`), so the lock-transition race in F-02 applies.

**Blocked?** Yes sequentially; **not reliably** under the concurrent lock transition.

**Inconsistent output?** If the change commits before T2 loads preferences, T2’s plan uses the new preferences and is internally consistent, but the score/objective may differ from T1’s view. If it commits after T2’s load, the committed plan reflects the old preferences. Preferences are soft, so this is not a hard-constraint failure, but it is a reproducibility and expectation problem. Historical metrics are also recomputed from live preferences at read time (F-07), so the displayed score can drift even after completion.

**Hard-constraint violation?** No. Preferences do not affect prohibited pairs or mandatory skills.

**DB integrity intact?** Yes. `teammate_preferences` has composite foreign keys to the roster and a unique rank; the service replaces the set atomically.

**Smallest safe solution:** Project row lock in `PreferenceService.replaceMyPreferences` before the lock/status check, plus a preference version or snapshot. For Engine 4, persist the preference snapshot or at least the metrics computed at completion.

### F.3 Scenario C — skill proficiency change during formation

**Question:** Can a student’s skill/proficiency change after T1 and before T2 commits?

**Possible?** **Yes, unconditionally.** `StudentSkillService.replaceMySkills` (`StudentSkillService.java:61–95`) deletes and replaces the student’s skills with no project lock, no preference-lock check, no active-job check and no version. Skills are not project-scoped, so even a project-scoped lock on one project would not cover a skill used by multiple projects. The formation loader reads live `student_skills` in both T1 (`FormationInputLoader.java:134–161`) and T2 (`FormationInputLoader.java:81–89`), and no skill snapshot exists.

**Blocked?** **No.** This is the only required scenario that is fully possible without any race: a student can change skills while a job is `READY` or during T2.

**Inconsistent output?** Yes. T1 and T2 can see different proficiency maps. A configuration that passed T1 feasibility can fail T2 (the engine may throw `NoValidFormationException`), or vice versa. If the change commits after T2’s load but before T2 commit, the committed plan may not satisfy a mandatory skill relative to the current student skills. The validator correctly validates the T2 snapshot, not the post-commit database state, so it will not catch this.

**Hard-constraint violation?** **Yes, relative to current data.** The plan is valid against the snapshot used by T2 but can violate `MANDATORY_SKILL` against the skills that are current when the job is read or when Engine 4 finalizes. This is the most serious correctness consequence in the audit.

**DB integrity intact?** Yes. `student_skills` has a uniqueness constraint on `(profile_id, skill_id)` and a proficiency check, but no table connects a candidate membership to the skill values used to validate it. Nothing is corrupted; the provenance is simply missing.

**Smallest safe solution:** The smallest correct fix is to persist the skill snapshot used by T1 and have T2 (and Engine 4) read that snapshot, or to lock/guard skill edits for students on a project with an active job. A skill-only snapshot is smaller than a full input snapshot but still requires a migration and a job foreign key. A guard alone (reject skill edits while any active job includes the student) is operationally simple but brittle for multi-project students. The snapshot is recommended because it also serves Engine 4 replay and audit.

### F.4 Scenario D — team-size change T1→T2

**Question:** Can `min/max/slack` change after T1 and before T2 commits?

**Possible?** Sequentially, no. `ProjectService.updateProject` (`ProjectService.java:78–101`) rejects a change to locked settings when `arePreferencesLocked(project)` is true (`:84–88`), and `changesLockedSettings` compares min/max/slack/deadline (`:204–209`). But the project is loaded with `findByIdAndMentorId` (`:81`), not a lock. The same lock-transition race as F-02 applies. Worse, `updateProject` writes every field of the managed entity; because `Project` has no `@Version` and no `@DynamicUpdate` (`entity/Project.java:24–69`), Hibernate’s default update includes `preferences_locked_at` and `status`. A stale entity can therefore write `preferences_locked_at = NULL` and `status = PUBLISHED`/`DRAFT`, silently unlocking preferences. `publishProject` (`ProjectService.java:157–173`) has the same stale-write risk: it loads without a lock, checks `DRAFT`, and can overwrite a status that `lockPreferences` concurrently changed to `PREFERENCES_LOCKED`. This is F-03, and it amplifies Scenarios A and B by reopening the lock.

**Blocked?** Yes sequentially; **not reliably** under concurrency.

**Inconsistent output?** Yes. T2 loads team sizes from the job’s `Project` during `FormationInputLoader.load` (`:96–103`). If a team-size change commits before that read, T2 uses the new sizes and is internally consistent. If the change commits after T2’s read but before T2’s commit, the committed teams can violate the current project settings. There is no team-size version check in T2.

**Hard-constraint violation?** Yes, relative to the current project settings. Team size is a structural hard constraint enforced by the planner and validator against the T2 input, but not against the post-commit project row.

**DB integrity intact?** Yes. `projects` has a CHECK on min/max/slack, but no table ties persisted candidate team sizes back to the project’s current settings.

**Smallest safe solution:** Project row lock in `updateProject`/`publishProject` before reading and writing, `@Version` optimistic locking and/or `@DynamicUpdate`, and a targeted update that never writes `preferences_locked_at` or `status` from a settings edit. In T2, record a team-size signature (or version) and recheck it before commit.

### F.5 Scenario E — constraint configuration update during formation

**Question:** Can the constraint configuration change after T1 records a version and before T2 commits?

**Possible?** This is subtler than the other scenarios, and the audit found a real gap (F-04).

- `ConstraintConfigurationService.replaceConstraints` (`ConstraintConfigurationService.java:78–124`) locks the project row (`findByIdForUpdate`, `:84`) and calls `rejectIfLocked` (`:149–170`). That method rejects `FORMED`/`APPROVED`/`COMPLETED` projects and rejects when an active `READY`/`RUNNING` job exists.
- T1 also holds the project row lock while it creates the `READY` job, so a constraint save that starts concurrently with T1 serializes behind T1. If T1 commits first, the save should see `READY`; if the save commits first, T1 loads the new version. The ordinary sequential paths are correct.
- **The gap:** the active-job check is a plain `existsByProjectIdAndJobStatusIn` SELECT, and the transaction has already performed a consistent read (the authenticated user lookup via `CurrentUserService`) **before** it acquires the project lock. Under MySQL’s default `REPEATABLE READ`, that first read establishes the transaction’s read view. If T1 commits `READY` after that view is established but before the save acquires the project lock, the `exists` check can use the older view and miss the `READY` job. The save can then commit a new constraint version while the job is `READY`.
- T2 does **not** hold the project row lock; it only locks the `formation_jobs` row (`FormationService.java:248`). Therefore a constraint save can acquire the project lock and commit during T2. T2’s version check (`:260–266`) is itself a consistent read. If the save commits after T2’s version-check read, T2 will not see the new version and can commit a `COMPLETED` plan under the old version. If T2 sees it, T2 fails with 409 and T3 marks the job `FAILED`.

**Interleaving that produces a stale completed plan:**

| Time | T1 | Constraint save | T2 |
| --- | --- | --- | --- |
| t0 | — | Starts, reads current user (read view S0; no active job) | — |
| t1 | Locks project, creates READY, commits | — | — |
| t2 | — | Waits for project lock, acquires it, `exists` uses S0 → misses READY, commits version N+1 | Starts, locks job, READY→RUNNING, reads version N, passes check |
| t3 | — | — | Runs engine, validates, persists, commits COMPLETED with version N |
| t4 | — | — | Current project version is N+1; completed plan honors N |

This is a code/isolation-derived race. It was **not** reproduced by the current test suite; there is no targeted Testcontainers test that creates the stale read view. Marking it **UNVERIFIED experimentally** is required, but the reasoning is concrete enough to block unconditional acceptance.

**Blocked?** Sequentially during a committed `READY` job, yes; during T2, not reliably.

**Inconsistent output?** Yes: a completed plan can be based on an outdated constraint version.

**Hard-constraint violation?** Yes, relative to the current version. The plan is valid for the recorded version, which is exactly why the version is recorded, but the system’s own rule is that an active run must not read two versions.

**DB integrity intact?** Yes. Constraint versions are immutable and uniquely keyed; nothing is overwritten. The issue is temporal consistency, not referential integrity.

**Smallest safe solution:** Have T2 acquire the same project row lock held by T1 and by constraint saves, with a consistent lock order (project → job), and hold it until T2 commits. Then a constraint save cannot commit during T2; after T2 commits, it sees `COMPLETED`. Alternatively, make the active-job check a locking/current read (e.g., lock the active job rows) and recheck the version under that lock at the end of T2. The project-lock approach is the simpler and more general fix and also helps Scenarios A/B/D if those services take the same lock. It should be paired with a targeted race test.

### F.6 Cross-scenario conclusion

| Invariant | Normal sequential path | Concurrent path |
| --- | --- | --- |
| Preferences lock freezes roster | Holds | **Can be bypassed** (F-02) |
| Preferences lock freezes preferences | Holds | **Can be bypassed** (F-02) |
| Preferences lock freezes team sizes | Holds | **Can be bypassed** (F-02/F-03) |
| Preferences lock freezes skills | **Does not hold** (F-01) | **Does not hold** (F-01) |
| Active job freezes constraints | Holds for committed READY | **Not absolute** (F-04) |
| Completed plan matches current constraint version | Holds at commit | **Can be stale** (F-04) |

### G.3 What the one concurrency test actually proves

`Engine3FormationConcurrencyIntegrationTest` uses a `@MockitoSpyBean` to pause the first run inside `formationEngine.form(...)` (`:57–65`). While the first request is paused, the second request receives 409 (`:78–81`). The first then completes and the test asserts one job, two candidate teams and four members (`:94–96`).

That is a real MySQL integration test for **active-job rejection when a committed `READY` row exists**. It does **not** prove:

- that two simultaneous T1 transactions serialize on the project row;
- that a `RUNNING` job is visible to the second request (it is not, because `RUNNING` is uncommitted);
- that roster/preference/team-size/constraint mutations are blocked during T2.

In fact, the test would still pass if T1’s project row lock were removed, as long as the first T1 commits `READY` before the second T1’s active-job check. The test name and V2.9’s description (“while the first run is still RUNNING”) overstate what is proved. The lock is real and code-inspected, but the test is not its proof.

### G.6 Isolation

`application.yml` does not set a transaction isolation level, and neither does any `@Transactional`. MySQL 8 defaults to `REPEATABLE READ`. That default is central to F-02 and F-04: the first consistent read in a transaction establishes a read view that later plain SELECTs reuse. This is not a bug in itself, but it must be documented and considered in every check-then-act guard. `FormationService` uses `TransactionTemplate` with default isolation, so T1/T2 are also `REPEATABLE READ`.

## H. Crash and Recovery Analysis

### H.1 Crash scenarios

| Crash point | Committed state | Candidate rows | Immediate impact | Recovery today |
| --- | --- | --- | --- | --- |
| After T1 commit, before T2 starts | `READY` job | None | Active-job check blocks new runs and constraint saves for that project | None; manual DB intervention |
| After T2 `markRunning` flush, before T2 commit | `READY` (T2 rolls back; `RUNNING` was never committed) | None | Same as above | None |
| During candidate persistence inside T2 | `READY` (entire T2 rolls back) | None | Same as above | None; atomicity prevents partial candidates |
| After T2 commit (`COMPLETED`) | `COMPLETED` job + all candidates | Complete | Consistent; if the HTTP response was lost, the client may retry and create a second job | None needed for data; duplicate-run risk (F-15) |
| T2 throws a normal exception | `READY` until T3 commits | None | T3 marks `FAILED` with a safe reason | T3 **if it commits**; if T3 fails, job stays `READY` |
| T3 itself fails (DB down, lock timeout, process crash during T3) | `READY` or `RUNNING` | None | Original API error; job stuck | None; no retry/monitor |
| Crash after T3 commit | `FAILED` | None | Terminal; rerun allowed | None needed |

### H.2 Correction to the V2.9 crash claim

V2.9 known limitation #4 says: “a process crash during T2 can leave a `RUNNING` job until manual intervention.” That is **incorrect for the current implementation**. `markRunning` is flushed but not committed until T2 commits; a process crash rolls it back. The job is left `READY`, not `RUNNING`. `RUNNING` would only be externally visible if the READY→RUNNING transition were committed in a separate transaction, which it is not. The practical impact is the same (a stuck active job), but the diagnosis and reaper query must target the correct state.

### H.3 Recovery options

| Option | Description | Advantages | Disadvantages | Suitable for synchronous V1? |
| --- | --- | --- | --- | --- |
| **A. Timeout-based scheduled reaper** | A scheduled job scans for `READY`/`RUNNING` rows older than a configurable threshold, locks each job row, rechecks status, and marks it `FAILED` with a safe reason/code. | Smallest operational change; no schema change; works across restarts; one class + one config property; can also record a metric. | Requires `@EnableScheduling`; timeout must exceed the longest legitimate run; multi-instance safe only with the job row lock/conditional update; reaper can wait on a long T2’s row lock. | **Yes — recommended** |
| **B. Lazy reaping on the next start request** | Before the active-job check, detect a stale `READY` job and fail it, then proceed. | No scheduler; very small. | Does nothing until someone tries to start; constraint saves can remain blocked; harder to reason about; not a recovery guarantee. | Acceptable as a stopgap, not as the primary recovery |
| **C. Durable queue / worker lease / heartbeat / retry** | Move formation to a queue with leases, heartbeats, idempotent workers and automatic retries. | Correct for async/multi-instance scale. | Largest change; new infrastructure; outside V1 scope and decision 65. | No |

### H.4 Recommended smallest recovery for V1

**Option A**, with these properties:

- Configurable `formation.job.stale-timeout` (for example, comfortably above the worst-case T2 duration) and a reaper interval.
- Per-row `findByIdForUpdate` and a status recheck before marking `FAILED`; never a blind bulk update. This prevents the reaper from failing a job that T2 is actively completing.
- If a reaper encounters a job whose row is locked by T2, it should skip/wait rather than fail it.
- A safe failure reason such as “The formation job exceeded its execution time and was marked FAILED”; a structured reason code is preferable (F-09).
- A metric/log for reaped jobs, so repeated timeouts are visible.
- No automatic retry: after `FAILED`, the mentor can start a new run. This preserves the synchronous contract and avoids duplicate plans.

Do **not** implement this in the audit; it is a V2.11 task.

### H.5 Idempotency and lost responses

If T2 commits `COMPLETED` but the HTTP response is lost, a client retry starts a new run because the previous job is terminal. That produces two `COMPLETED` jobs and two candidate sets for the same project. This is not corruption, but it complicates Engine 4 finalization and audit. A future `Idempotency-Key` on `POST /formation-jobs` (unique per project/key) or a “latest completed job” selector would help. `FormationJobRepository.findFirstByProjectIdOrderByCreatedAtDescIdDesc` already exists and can support “latest” semantics, but no idempotency key exists.

## I. Algorithm Correctness, Scoring, and Determinism

### I.1 Property table

| Property | Assessment | Evidence |
| --- | --- | --- |
| Assignment integrity: each eligible student exactly once | Correct | Construction places each ordered student once; `FormationPlanValidator` checks duplicate assignment, eligible membership, team count and total assigned count (`FormationPlanValidator.java:48–94`) |
| Team sizes match the Engine 2 plan | Correct | Engine checks capacity equals student count (`FormationEngine.java:50–55`); validator compares each team’s planned/actual size with the planner (`:42–64`) |
| Prohibited pairs never share a team | Correct | Construction rejects forbidden members (`FormationEngine.java:265–271`); local search checks swaps (`:362–384`); validator rechecks (`FormationPlanValidator.java:169–179`) |
| Mandatory skill per team at minimum proficiency | Correct | Construction tracks per-team coverage and prunes with suffix counts (`FormationEngine.java:181–201`, `:265–287`); local search preserves coverage (`:376–398`); validator rechecks (`FormationPlanValidator.java:181–201`) |
| Rank 1 = 1.0, rank 2 = 0.5 | Correct | `CompatibilityScorer.java:10–19`, `:52–66`; `CompatibilityScorerTest` |
| Mutual preferences counted twice | Correct | Directed scoring iterates each requester; mutual pairs contribute twice; tested by `scoreTeam_directedRanksAndMutualPreferences` |
| No `ProjectConstraint.weight` in scoring | Correct | `ProjectConstraint` carries `weight = 1.0` for hard rules, but `CompatibilityScorer` never reads it; its documentation explicitly says no constraint weight or skill-diversity term |
| Unsatisfied count excludes students without preferences | Correct | `CompatibilityScorer.java:87–113`; unit test |
| No preference target on the same team | Correct | Directed contribution only adds when `teamOf` matches the preferred student |
| Canonical team ordering and names | Correct | `toPlan` sorts by size desc, smallest member, original ordinal (`FormationEngine.java:492–528`); `TeamNameGenerator`; validator rechecks |
| Deterministic tie-breaking | Correct in-process | Seed-derived `studentRank`/`teamRank`/`planTieBreak`; stable comparators end in student id/team index; `DeterministicTieBreakerTest` and `FormationEngineTest` same-seed cases |
| Bounded construction | Correct | `max-nodes = 250000`; each placement attempt increments `nodes` and throws at the budget (`FormationEngine.java:195–199`) |
| Bounded local search | Correct but not time-bounded | `max-improvement-passes = 100`; each pass scans team pairs and member pairs; no wall-clock timeout |
| Global optimality | **Not claimed** | Engine javadoc: “bounded heuristic… never claims global optimality”; only a bounded 1-swap neighborhood |
| Cross-JVM determinism | Not empirically verified | The algorithm is designed for it (seed-derived, no JVM-dependent iteration affecting sums), but no golden/cross-JVM test exists |

### I.2 Scoring detail

`CompatibilityScorer.scoreTeam` (`:52–66`) iterates each member and each of that member’s preferences; if the preferred student is in the same team, it adds the preference weight. Rank 1 is 1.0, rank 2 is 0.5. Mutual preferences are two directed rows and therefore count twice. The scorer deliberately does not use `ProjectConstraint.weight` and does not add a skill-diversity term. All achievable totals are sums of 1.0 and 0.5, which are exactly representable in binary floating point, so exact `Double.compare` is safe. The validator recomputes team scores, total score, unsatisfied count, students-without-preferences and the plan tie-break and rejects any mismatch (`FormationPlanValidator.java:81–124`). This is strong defence in depth.

### I.3 Determinism and tie-breaking

- `DeterministicTieBreaker.studentRank(seed, studentId)` and `teamRank(seed, ordinal)` use a fixed mix function; no random source is consulted after the seed is chosen.
- Construction sorts students by mandatory coverage desc, prohibited degree desc, seed rank, then student id.
- Candidate teams sort by covered-unmet desc, incremental preference desc, seed team rank, then team index.
- Local search iterates teams in ordinal order and members in sorted order, uses best-improvement, and applies the best strictly better swap. Equal objectives keep the earlier candidate, which is deterministic.
- The final plan is re-sorted canonically and its tie-break is recomputed with canonical team ordinals, so the recorded tie-break matches the validator.
- The seed is generated with `SecureRandom.nextLong() & Long.MAX_VALUE`, so it is non-negative and recorded on the job.

The in-process determinism test passes. A cross-JVM golden test (fixed input + seed → byte-for-byte plan) is missing; the code is likely deterministic across JVMs because all sums are exact and all iteration orders are explicitly controlled, but that is **UNVERIFIED** by the test suite.

### I.4 Bounded search and complexity

- The node budget bounds construction attempts, not wall time.
- The local search is bounded by `max-improvement-passes`, but one pass is `O(T² · S²)` in team count and member count; 100 passes on a large cohort can be expensive.
- There is no request timeout, cancellation or progress metric. A large but feasible project can occupy a request thread and a DB transaction (T2) for a long time. The synchronous design assumes modest class sizes.
- Exhausting the node budget fails the run; it never returns a partial plan. That is the correct safety choice.

### I.5 Algorithm verdict

The algorithm is **correct for the stated hard constraints and objective** and does not overclaim optimality. The main algorithmic risks are not correctness of a single plan but (a) input changes between load and commit, (b) lack of a wall-clock bound, and (c) missing provenance for replay. Those are covered by F-01, F-04, F-10 and F-20.

- `finalized_teams.finalized_at` and `finalized_team_memberships.assigned_at` default to `CURRENT_TIMESTAMP` (`V3:142–174`).
- MySQL `TIMESTAMP` is second-precision; the service’s `sameStoredInstant` tolerance in `ProjectService` acknowledges this (`ProjectService.java:211–223`).
- There is no `updated_at` on `formation_jobs` and no `version` column on candidate/job entities, so optimistic concurrency is not available without a migration.

### J.5 Database verdict

The core candidate/finalized invariants are genuinely database-enforced and well tested. The gaps are mostly **semantic** (roster membership of candidate members, project/job consistency, one active job, provenance) rather than referential corruption. This is why there is no CRITICAL DB finding, but F-02/F-04/F-08/F-17 remain material.

## K. API Authorization and Security

### K.1 Authentication

- `SecurityConfig` permits only registration, login, email verification and health; every other request is `authenticated()` (`security/config/SecurityConfig.java:41–50`).
- The API is stateless, CSRF-disabled (appropriate for a token API), with a JWT resource server and custom entry point/denied handler (`:51–57`).
- `CurrentUserService` resolves the JWT subject to a database user, rejects malformed subjects, inactive users and missing users with 401 (`CurrentUserService.java:41–59`). The role is read from the database, never trusted from the token (`:61–75`). This is correct.

### K.2 Authorization

| Check | Implementation | Result |
| --- | --- | --- |
| Only mentors can start/read/list formation jobs | `requireCurrentUserWithRole(..., MENTOR)` | 403 for students/admins |
| Only the owning mentor can start | T1 compares `project.mentor.id` and reports 404 on mismatch | 404 for another mentor |
| Only the owning mentor can read a job | `requireOwnedProject` + `findByIdAndProjectId` | 404 for another mentor; cross-project job id is scoped out |
| Only the owning mentor can list jobs | `requireOwnedProject` + project-scoped query | 404 for another mentor |
| Unauthenticated | Security filter chain / `CurrentUserService` | 401 |

The ownership test covers unauthenticated (401), student/admin (403), another mentor (404), nonexistent project (404), and nonexistent job (404). It does not explicitly test “owner uses their own project path with a job id from a different project”; the repository query `findByIdAndProjectId` makes that a 404 by construction, but the test gap remains (F-14).

### K.3 Error safety

- `GlobalExceptionHandler` maps `BaseException` to its declared status/message, validation to 400, unreadable JSON to 400 with a generic message, access denied to 403, authentication to 401, and everything else to a generic 500 (`GlobalExceptionHandler.java:28–117`).
- Stack traces are logged, never returned. `Engine3FormationFailureIntegrationTest` proves the injected failure text and exception class do not leak into the job error message.
- `FormationException` messages are safe and human-readable; T3 stores them or a generic internal message, truncated to 2,000 characters.
- `HttpMessageNotReadableException` is handled, so unknown JSON fields are rejected with 400 (also enabled by `fail-on-unknown-properties: true`).

### M.2 Contract gaps that block a clean Engine 4

1. **No provenance from finalized team back to the run.** Engine 4 cannot answer “which formation job, candidate team, constraint version, seed and algorithm version produced this finalized team?” The schema has no columns for it.
2. **No input snapshot.** Engine 4 cannot reproduce or defend a finalized plan if roster/preferences/skills/team sizes/constraints have changed. `completed_at` + seed + algorithm version is not enough.
3. **No stable historical metrics.** Re-reading a completed job recomputes unsatisfied/without-preferences from live preferences, so an audit can see a different number later.
4. **No structured failure taxonomy.** A UI/automation cannot distinguish infeasible input, search-limit exhaustion, invalid plan and internal failure without parsing text.
5. **No candidate lifecycle.** Every candidate team is `DRAFT`; there is no selected/rejected/approved status, no finalization service, and no project `FORMED` transition.
6. **No finalization API.** `FinalizedTeam`/`FinalizedTeamMembership` entities exist, but there is no service or controller to finalize a plan. Engine 4 would need to add them; the audit did not modify schema or APIs.
7. **Deletion destroys provenance.** `ON DELETE CASCADE` from `formation_jobs` to candidates means deleting a job erases the plan. Engine 4 should use `RESTRICT`/archive semantics for finalized or audited runs.
8. **No idempotent finalization.** Finalization must be idempotent and lock the project/candidate set; no such mechanism exists yet.

### M.3 Engine 4 readiness verdict

Engine 3 exposes enough to **display** a completed candidate plan and its seed/algorithm/constraint version. It does **not** expose enough to **finalize, audit or replay** that plan. Engine 4 should begin only after V2.11 adds the input snapshot and finalization provenance columns/services, or as a coordinated V2.11 + Engine 4 milestone.

### N.2 Final acceptance decision

**CONDITIONALLY ACCEPTED**

**Explanation.** Engine 3 is correct and well tested for the synchronous, single-actor V1 path. The independent build is green (310/0/0/0, exit 0, 06:53), the algorithm enforces its stated hard constraints, the plan validator is strong, persistence is atomic, the candidate/finalized DB invariants are protected, and authorization is sound. There are **no CRITICAL findings** and no evidence of unconditional data corruption or access-control bypass.

Acceptance is **conditional** on the following, which must be completed before Engine 3 is used in a concurrent/multi-user production setting or treated as the foundation for Engine 4 finalization:

1. Close **F-01** (skill mutation) with a snapshot or an active-job skill lock/guard.
2. Close **F-02** (roster/preference TOCTOU) and **F-03** (stale project write) with project row locks, optimistic/versioned updates and targeted column updates.
3. Close **F-04** (constraint-freeze race) by having T2 hold the project row lock, or by making the active-job/version checks locking/current reads, and add a deterministic race test.
4. Add the **F-05** crash reaper (Option A) and the **F-09** structured failure reason.
5. Add the **F-10** input snapshot and the **F-08/F-11** Engine 4 provenance/finalization contract before Engine 4 finalizes plans.

### N.3 Recommended next task

**V2.11 — Engine 3 Reliability and Consistency Hardening**

**Scope**

1. **One project-level lifecycle lock.** Make every input mutator (`RosterService.addToRoster/removeFromRoster`, `PreferenceService.replaceMyPreferences`, `ProjectService.updateProject/publishProject`, `StudentSkillService` where applicable, `ConstraintConfigurationService.replaceConstraints`) acquire the project row with `findByIdForUpdate` **before** its lock/status/active-job check. 2. **Skill snapshot or active-job skill guard.** Preferred: persist the T1 input snapshot (roster ids, preference rows, skill proficiencies, team sizes, constraint version/rows) and have T2 read it. Minimum: reject skill edits for students on a project with an active job, and revalidate mandatory skills under the lock before T2 commit.
3. **Crash recovery.** Add `@EnableScheduling` and a stale-job reaper with a configurable timeout, per-row `findByIdForUpdate`, status recheck and a safe failure code. Do not auto-retry; allow a new run after `FAILED`.
4. **Structured failure reporting.** Add nullable `failure_code` and `failure_phase` to `formation_jobs` (V6) and set them in T3.
5. **Constraint mutability after completion.** Block constraint changes when a completed job with candidates/finalized teams exists, or explicitly mark the project/plan stale and require a re-run.

### N.4 Deviations from V2.8/V2.9 decisions and claims

| Decision/claim | Stated position | Audit finding |
| --- | --- | --- |
| Decision 57 (constraint mutability) | “The active-job check prevents an in-flight run from reading two versions.” | Not absolute. The check is a plain SELECT after a consistent read, and T2 does not hold the project lock; a version can commit during T2 after the version recheck (F-04). The normal sequential path is correct. |
| Decision 66 (formation transactions) | “T3 still guarantees that an in-flight job cannot remain `RUNNING` after a failure.” | Conditional. T3 only guarantees this if T3 itself commits. If T3 fails or the process crashes, the job can remain `READY` (not `RUNNING`, because T2’s `RUNNING` is uncommitted). The practical recovery gap remains (F-05). |
| Decision 73 (frozen references) | No roster/preference/team-size/skill snapshot; rerun uses current inputs. | Confirmed. The audit additionally finds that the FormationService javadoc’s claim that lifecycle rules keep inputs unchanged for an active job is **not true for skills** (F-01) and only partially true for roster/preferences/team size because of the lock-transition races (F-02/F-03). |
| V2.9 limitation #3 | “Roster not frozen during a run; RosterService does not currently block roster changes while a job is READY/RUNNING.” | Misleading. RosterService **does** block changes after the preferences lock sequentially; the real gap is the lock-transition TOCTOU race (F-02). The limitation should be rewritten. |
| V2.9 limitation #4 | “A process crash during T2 can leave a `RUNNING` job.” | Incorrect. A crash rolls T2 back; the job is left `READY`. The reaper must target committed `READY` (and any future committed `RUNNING`) rows. |
| V2.9 test citations | `startFormation_enforcesMandatorySkill`, `startFormation_enforcesProhibitedPair`. | Actual names are `startFormation_enforcesMandatorySkillPerTeam` and `startFormation_separatesProhibitedPair`. Documentation drift (F-19). |
| V2.9 concurrency claim | “Holds T2 and observes 409 for the second request.” | True, but it proves rejection against a committed `READY` row, not `RUNNING` visibility or T1 serialization. The test would pass without T1’s project lock (G.3). |
| V2.9 “No new migration required” | Engine 3 adds no V6. | True for V2.9. V2.11 will need a V6 for snapshots/provenance/failure codes if the recommended fixes are implemented. |
| V2.9 build time | `09:57 min`. | Current independent run: `06:53 min`, same 310/0/0/0 result. Timing is environment-dependent; the pass/fail content is identical. |

### N.5 Audit conclusion

Engine 3 is a solid, well-structured, green implementation with a correct single-plan algorithm, strong validation, atomic persistence, and sound authorization. Its weaknesses are concentrated in **concurrent input mutation, crash recovery, historical/provenance durability, and the gap between what the one concurrency test proves and what the design assumes**.

The correct next move is **not** to start Engine 4 finalization immediately. The correct next move is **V2.11 — Engine 3 Reliability and Consistency Hardening**, closing F-01 through F-05 and adding the F-08/F-10 provenance/snapshot contract. After V2.11, Engine 3 can be accepted as a concurrency-safe, crash-recoverable foundation, and Engine 4 can begin with a defensible audit trail.

**Final decision: CONDITIONALLY ACCEPTED.**
